# Beta accounts and admin backend plan

Status: deferred, 2026-11-08. The first beta uses the smaller shared-code plan in [beta-code-gate-plan.md](beta-code-gate-plan.md). This document remains a possible later account design; no individual accounts or admin features are implemented yet.

## Goal and initial scope

Run Sky Peek on a Hostinger Node.js Web App at the root of its own subdomain. Only invited testers and administrators can use the app. An administrator can invite, suspend, and remove testers without editing the database. Keep the weather experience and existing browser-local settings working while beta access is added.

The first release supports a small group of friends. Invitation and password-reset links are copied from the admin area and delivered personally. Automated email is a later step, so no SMTP account or email vendor is required for the first beta. The link recipient sets a password, then signs in with email and password. Link possession is treated as proof of control for this small manually delivered beta; automated email verification is needed if sign-up expands beyond personally delivered invites.

## What the administrator can do

| Area | First release |
| --- | --- |
| Invites | Create a one-use invite for a specific email; choose an expiry; copy its link; see pending, redeemed, expired, and revoked invites; revoke or reissue. Display the full token only when created. |
| Testers | List email, role, status, invite/recent sign-in dates; suspend or restore access; invalidate all sessions; create a one-use password-reset link; delete an account when requested. Prevent an administrator from removing the last active admin. |
| Beta controls | See a small status page with active testers, pending invites, recent failures, app version, and database health. Show or hide an optional beta notice with an end date. |
| Feedback | Tester form for a short bug or idea report; admin list with open/resolved status and export. Keep submission optional and avoid collecting precise location, provider keys, and weather history automatically. |
| Audit | Record admin changes, invitation redemption, account suspension, and failed sign-ins without storing passwords, full tokens, or provider keys. |

Keep forecast weights, provider polling, request ceilings, and data-source credentials in reviewed code or server configuration. They should not become casual admin toggles during beta. The existing `Settings` screen remains personal to each browser.

## Application flow

1. An unauthenticated visitor sees `/login`, `/accept-invite`, or `/reset-password` as appropriate. App pages (`/`, `/lab`) and their live API routes require a valid session. `/design` should be admin-only or omitted from the beta build.
2. The admin creates an email-bound invite. The server generates a cryptographically random token, stores only its hash, and shows the full link once. The link expires and can be used only once.
3. The invited tester opens the link, sets a password, and receives a new session. Sign-in and sign-out work on later visits. An admin can revoke invites, suspend an account, and terminate its sessions immediately.
4. Password recovery initially uses a one-use reset link generated by the admin and shared directly with that tester. A later email integration can deliver reset links automatically without changing the underlying token rules.
5. The admin area lives under `/admin`, inside the same Next.js application and MySQL database. Every admin action checks the administrator role on the server; hiding controls in the interface is not authorization.

## Server and data design

- Use Hostinger MySQL for `users`, `invites`, `sessions`, `password_reset_tokens`, `audit_events`, `feedback`, and a small `beta_config` record. Add versioned schema migrations. Keep migrations separate from `next build` so a build cannot unexpectedly mutate the database.
- Connect from the Hostinger Node.js app through a small, bounded MySQL connection pool. Hostinger documents `127.0.0.1` as the database host for its Node.js apps; database name, user, and password are runtime environment variables.
- Keep passwords as modern slow password hashes (Argon2id if supported by the chosen runtime package, otherwise bcrypt with an appropriate cost). Never store plaintext passwords.
- Use random database-backed session tokens with only a hash stored server-side. Set an `HttpOnly`, `Secure`, `SameSite=Lax` cookie scoped to the subdomain. Give sessions an expiry; rotate on sign-in and invalidate on logout, suspension, password change, and account deletion.
- Check authorization in the shared server data-access layer and again in every protected Route Handler or Server Action. Protect writes against cross-site request forgery and rate-limit sign-in, invite redemption, reset, and feedback requests. Do not let a client-supplied role or email determine authority.
- Return generic sign-in and reset errors. Add `Cache-Control: no-store` for account pages and authenticated API responses. Do not put tokens in logs or analytics. Clear invite/reset tokens from browser history after redemption.
- Ensure the deployment has an initial admin bootstrap procedure that is one-time, requires a high-entropy setup secret kept in Hostinger environment variables, and closes permanently once an admin exists. Test that a fresh database cannot expose `/admin` to an anonymous visitor.

## Browser data boundary

Accounts establish beta access; they do not automatically sync browser data. Saved places, alert settings, optional provider keys, diagnostics, and the request ledger currently use localStorage. Accuracy and safeguard records use IndexedDB. Leave those local for the first beta. Do not copy optional provider keys into MySQL or make a shared key available to browser code. If account-wide settings or accuracy collection become a goal, design that migration separately with a privacy and request-budget review.

The weather service and many radar layers fetch directly from each visitor's browser. Login gates the app and its own API routes, but it does not make third-party weather endpoints private or create a shared request quota. Track Hostinger usage and upstream 429s during the beta; do not infer a safe account-wide ceiling from the current per-browser ledger.

## Implementation sequence and acceptance checks

1. **Schema and configuration:** Add MySQL access, migrations, required-variable validation, health checks, and local test database setup. Keep build usable without production credentials. Verify migration on a clean database and repeatability on an existing one.
2. **Identity:** Add one-time admin bootstrap, invite acceptance, password hashing, sign-in/out, reset, sessions, and server-side gates for pages and existing `/api` routes. Verify unauthenticated requests, expired/reused links, suspended users, session revocation, and cookie behavior.
3. **Admin area:** Add invitation and tester management, bounded audit log, and beta notice. Verify tester/admin role separation, last-admin protection, and concurrent invite redemption.
4. **Feedback and support:** Add the tester feedback form and admin queue/export. Verify text limits and that sensitive browser data is not submitted implicitly.
5. **Hostinger rehearsal:** Set up a private subdomain deployment and MySQL database, configure runtime variables, run migrations and bootstrap, then test a full invite-to-sign-in path over HTTPS. Confirm `/design` access policy and each live API route. Review resource graphs and error logs before sending invites.

## Decisions before coding

- Confirm whether personally shared invite/reset links are acceptable for the first beta, or whether email delivery must be included from day one. The proposed first release uses personal delivery.
- Confirm whether testers need saved places and settings across devices. The proposed first release keeps them in each browser.
- Choose the exact subdomain and confirm the Hostinger plan supports Node.js Web Apps. The domain determines cookie scope and the production URL used in invitation links.
